# Skill Authoring Conventions

**Two hosts install this plugin.** Claude Code reads `.claude-plugin/plugin.json`; Cursor reads `.cursor-plugin/plugin.json`, which declares paths into the *same* `skills/` and `agents/` directories — there is never a second copy of a skill. Cursor's component contract is stricter than Claude Code's in two ways that don't fail loudly here: a skill's `name` must equal its folder name, and every skill and agent needs a `description`. `tools/docs_sync.mjs --check` gates both, plus version parity across all four manifests (`.claude-plugin/plugin.json`'s `version` is the source of truth). A new skill or agent therefore needs nothing Cursor-specific — just don't break those two rules, and bump every manifest together.

**`bigin-skills` depends on no other plugin.** The dependency direction is one-way — `product-rebuild-skills` (and anything else) may reference `bigin-skills`; nothing here may reference them. A skill, agent, or reference file must never cite a path, playbook, or section number that lives outside this repo as the source for what it writes: the other plugin is versioned separately, may not be installed at all, and a citation that dangles turns a stated authority into a dead link (v1.66.0 shipped exactly that — `profile-flutter.md` cited a `product-rebuild-skills` playbook that did not exist in the installed version). Reference material a profile needs gets **stated in full here**. External links are fine for third-party documentation; another BigIn plugin is not third-party documentation.

**SKILL.md files:**

- Body ≤500 lines, and **keep it under ~400** — move supporting detail into `references/`. Verbatim print templates, per-profile matrices, and argued edge-case rationale are reference material; the per-run instruction that points at them is not. When the same rule appears in N per-profile blocks, the fix is one table, not N tidier blocks.
- **Every skill needs `evals/evals.json`** — a non-empty array of `{query, should_trigger}` with at least one case each way. `tools/docs_sync.mjs --check` fails the commit without it; it was a convention for four audits running and got skipped by three separate new skills, so it is now a gate.
- A skill that proposes and stops before applying (`sprint-distill`, `harness-audit`) sets **`disallowed-tools: Edit Write NotebookEdit`**. The restriction covers exactly the invoking turn and clears when the user replies, which is the same boundary the propose-then-stop phase already has — so the discipline becomes mechanical instead of prose. Don't add it to a skill that writes anything before its first stop.
- Cite a sibling skill's file through **`${CLAUDE_PLUGIN_ROOT}`**, not a bare repo-relative path — the plugin's install directory isn't the working directory, and the variable is substituted in skill content.
- `description:` frontmatter is the trigger — and it is **always loaded**, for every skill, on every turn. Budget: **≤350 chars, aim ~250.** One clause on what the skill does, then 3–4 representative triggers. Matching is semantic, not literal string lookup — fourteen phrasings match no better than four.
- **English only, everywhere** — descriptions, trigger phrases, eval fixtures, headers, body prose. No bilingual pairs.
- "Do NOT use for…" prose belongs in a body `## When not to use` section, where it costs nothing until the skill is invoked — never in `description:`.
- All `references/` paths in a SKILL.md are relative to that skill's own `references/` directory
- Don't rely on a rule generalizing across items — if it applies to every profile/file/case, be explicit. But **explicit ≠ copy-pasted**: a per-item table (one row per profile, columns for what differs) is explicit *and* single-source. N near-identical prose blocks drift the moment one of them is edited — that's what `references/scaffold-delegation.md` replaced.

**Generated files (templated in `references/`, written into target repos):**

- Keep each generated file SHORT — terse, scannable. A rule nobody reads is worse than no rule.
- All `.claude/rules/*.md` templates must carry `paths:` frontmatter. Unscoped rule files count against the always-loaded budget and must be ≤40 lines.
- Never duplicate rule content across generated files; reference the single source. The generated `CLAUDE.md` is always-loaded, so it holds only what must be true *before* any file is in context — a rule that belongs to a path goes in that path's scoped rule file, with at most a one-line pointer in `CLAUDE.md`.
- `AI_TASK_GUIDE.md` is a pointer to `task-workflow`, deliberately. Never restate the workflow's steps or formats there — the two diverged that way once already.
- Don't write context-management prose (what to preserve on compaction, when to `/clear`, piping output) into a generated `CLAUDE.md`. The `PreCompact` hook handles state deterministically, and the model manages its own context.
- A CHANGELOG.md entry that changes content copied verbatim into target repos (`files-shared.md`, `knowledge-bundle.md`, `profile-*.md`) may include a fenced ` ```patch ` block so `bigin-harness-setup`'s patch mode (Phase 1a) can apply it to already-scaffolded repos automatically: `target` (path as generated in a repo), `anchor` (exact existing substring), `insert: after|before|replace`, then `---`, then the content. Omit the block entirely if the change doesn't reduce to one clean anchor match — patch mode skips-and-flags anything it can't match exactly, so no block just means "no auto-patch," not an error.
- For a wholly new file with no existing anchor to patch against (e.g. a new guard script) — use `mode: create-if-missing` instead of `anchor`/`insert`: `target`, then `---`, then the full file content. Patch mode writes it only if `target` doesn't already exist in the repo; it never overwrites a file that's already there, hand-edited or otherwise.
- **One guard body, two hosts — never fork a guard.** The nine `.claude/guards/*.mjs` scripts run under both Claude Code (`.claude/settings.json`) and Cursor (`.cursor/hooks.json`). Every host difference belongs in `.claude/guards/lib/hook-io.mjs` (`readPayload`/`sessionKey`/`toolCall`/`toolOutput`/`projectDir`/`compactTrigger`/`isWriteShaped`/`isRiskyCall`/`emitDecision`/`emitContext`); a guard must never read `data.tool_input` or print a `hookSpecificOutput` envelope directly, and there must never be a Cursor-specific copy of any guard. Two invariants that fail *silently* if you break them: `sessionKey()` must prefer `conversation_id` over `session_id` (otherwise `canary-seed.mjs` seeds one filename and `injection-gate-guard.mjs` reads another, and stage 3 goes inert under Cursor with nothing failing), and `emitDecision()` must degrade `ask` to `deny` under Cursor (whose `preToolUse` response has no `ask`) rather than falling through to allow. **Test every guard change against both payload shapes** — a Cursor payload is the same stdin JSON with `cursor_version`/`workspace_roots`/`conversation_id` set and `tool_output`/`trigger` in place of `tool_response`/`compaction_trigger`. `bigin-harness-setup/references/hook-guard.md` → `## Testing a guard by hand` carries both recipes.
- **`.cursor/hooks.json` registers with no matchers, so guards must self-filter.** Cursor's matcher semantics differ per event and a non-matching matcher turns a gate off silently, so the harness omits them — which means every guard sees every tool call. `spec-gate-guard.mjs` filters on `isWriteShaped()` (a Read must not be gated) and `injection-gate-guard.mjs`'s stage 2 filters on `isRiskyCall()` (a Read must not consume the one-shot flag; stage 3's canary check deliberately still runs on everything). Both filters are shape-driven, not tool-name-driven, because Cursor's tool names aren't Claude Code's — this is also why `spec-gate-guard.mjs`'s `changeSize()` keys on `edits`/`old_string`/`content` rather than on `Edit`/`MultiEdit`/`Write`. If you add a matcher to `.cursor/hooks.json`, you've reintroduced the failure mode the omission exists to prevent.
- **Every stdin-reading guard wraps its payload parse, and the failure direction is per hook event.** `PreToolUse` gates (`bash-guard`, `spec-gate-guard`, `bugfix-test-guard`, `commit-msg-guard`, `injection-gate-guard`) fail **closed** via `readPayload(name)`: a one-line stderr diagnostic naming the script, then `exit 2`. A bare `JSON.parse(readFileSync(0, 'utf-8'))` throws, and an uncaught Node exception exits 1 — which both hosts treat as *non-blocking*, so the gate silently stops gating. `PostToolUse`/`SessionStart`/`PreCompact` guards (`injection-scan-guard`, `session-resume-check`, `canary-seed`, `precompact-snapshot`) can't block, so they pass `{ failClosed: false }` and exit 0 quietly. Test any guard you touch with both malformed JSON and empty stdin. `commit-msg-guard.mjs` is the one exception to watch: its `readPayload` call must sit *inside* `subjectFromToolInput()`, because the outer catch's allow-on-unreadable is for a missing commit-message file in argv mode. Cursor adds a second layer: it fails open on a crashed or timed-out hook unless the `.cursor/hooks.json` entry sets `failClosed: true`, so that flag belongs on exactly those five blocking gates and on none of the other four.
- **Guard scripts are app code once they land — write them lint-clean at the source.** The `nuxt` and `next` profiles lint `.claude/guards/**` along with everything else, so a guard authored in this repo (which has no ESLint) in a style those configs reject breaks `pnpm lint` in every repo that installs it. The PostToolUse lint-fix hook can't rescue it: Phase 5-2 writes the guards and Phase 5-3 registers that hook, so every guard is already on disk before anything is watching to fix it. Match `@stylistic`'s defaults, which is what `@nuxt/eslint` applies — the two that have actually bitten: **single quotes with no `avoidEscape`** (`'\'\''`, never `"''"` — copy `bash-guard.mjs`'s scrub line) and **`operator-linebreak: before`** (a trailing `??` or `=` at end-of-line is an error; break *before* the operator). To check a change, extract the ` ```javascript ` blocks to files and run ESLint with `stylistic.configs.customize({ indent: 2, quotes: 'single', semi: false, commaDangle: 'never', braceStyle: '1tbs' })` — the exact ruleset `nuxt-scaffold` ships.
- **Never hand-quote a test payload inline** (`echo '{"tool_input": …}' | node …`) — nested quotes silently produce malformed JSON, which now exits 2 with the diagnostic above rather than masquerading as a pass. Use the heredoc-to-file recipe in `bigin-harness-setup/references/hook-guard.md` → `## Testing a guard by hand`, and assert on exit codes.
- `bash-guard.mjs` is the load-bearing gate — if you change its regexes, test: block `--no-verify`, `git commit -n`, `git push --force`; allow `--force-with-lease`, normal commits, messages merely containing `-n`.
- `bugfix-test-guard.mjs` is a load-bearing gate — if you change its fix-detection regex or test-path patterns, test: block `git commit -m "fix: x"` with no staged test file; allow the same commit once a `*.test.ts`/`*.spec.ts`/`_test.go`/`_test.dart`/`tests/**` file is staged — **test `integration_test/foo_test.dart` explicitly**, since it is matched by the `_test.dart` filename rule and by no directory rule, which is exactly the case that silently blocked Flutter fixes before v1.66.0; allow when the message contains `[no-test]`; allow non-fix messages (e.g. `feat: x`); allow when every staged file matches the docs/config allowlist; allow non-`git commit` commands and `git commit` with no `-m`. Its message extraction shares `commit-msg-guard.mjs`'s `(?:--message|-[a-zA-Z]*m)` form — test the bundled flag too (`git commit -am "fix: x"` with no test blocks; with a test staged allows).
- `commit-msg-guard.mjs` is a load-bearing gate — if you change its type list, subject regex, or length cap, test: block `git commit -m "fixed the parser"` and `git commit -m "Update README"`; allow `feat: x`, `fix(api)!: x`, and a subject at exactly 100 chars; block one at 101; allow `Merge branch 'main'`, `Revert "feat: x"`, `fixup! feat: x`, `git commit --amend --no-edit`, and non-`git commit` commands; and check the bundled-short-flag form both ways (`git commit -am "wip"` blocks, `git commit -am "feat: ok"` allows). **It has two entry points and both need testing.** PreToolUse (stdin payload, no argv): the cases above. commit-msg file mode (`node commit-msg-guard.mjs <path>`): a subject after git's `#` comment template passes; a non-conforming one after the same template blocks; a body plus a scissors line doesn't confuse subject extraction; a blank/comment-only file and an unreadable path both allow (exit 0). Its `fix:` requirement is what makes `bugfix-test-guard.mjs` reachable — loosening this one silently weakens that one.
- `spec-gate-guard.mjs` is the other load-bearing gate — if you change its allowlist/threshold, test: block a non-trivial edit with no/unapproved `PLAN.md`; allow the same edit once `PLAN.md` has `Status: approved`, and allow edits under the trivial-path allowlist or ≤20-line threshold regardless of plan status. Its write-shape self-filter is a fourth test set — test: a `Read`-shaped call (`file_path` only, no `content`/`old_string`) exits 0 even with a huge file and no plan, and a `Write` carrying `old_string`/`new_string` instead of `content` is still sized as an edit rather than falling through to `Infinity`. Its trivial-path allowlist has a Flutter case worth its own assertion: a >20-line write to `integration_test/foo_test.dart` must be **allowed** — it is matched by the `_test.dart` filename rule and by no directory rule, the same gap that silently blocked Flutter flow tests before v1.68.0, and the mirror image of the `bugfix-test-guard.mjs` case above. Its generated-artifact exemptions are a second test set — test: allow a large `graphify-out/**` write (tracked by design, so the git-ignore check can't cover it) and a large write to a git-ignored path; still block a **tracked** file that merely matches a `.gitignore` pattern (the check is deliberately index-aware — no `--no-index`), a near-miss name like `src/graphify-outsider.ts`, and any non-trivial edit outside a git repo. Its `Branch:` check is a third test set — test: block a non-trivial edit when `PLAN.md`'s `Branch:` disagrees with `HEAD`; allow when they match, when the plan has no `Branch:` line at all (pre-v1.50 plans), and when git can't answer (detached `HEAD`, no repo) even on a mismatch; a mismatched plan must still allow trivial paths and ≤20-line changes.
- `injection-gate-guard.mjs` (paired with `injection-scan-guard.mjs`) is a third load-bearing gate — if you change the freshness window or `injection-scan-guard.mjs`'s `INJECTION_PATTERNS`, test: a fresh flag on the next Bash/Write/Edit/WebFetch/mcp__ call returns `permissionDecision: "ask"` and the flag file is deleted after; a stale flag (older than the freshness window) passes through silently; a scan of benign fetched content (e.g. "we can safely ignore this warning") never writes a flag. Its stage-3 canary check is a fourth test set — if you change it, test: a canary token in a `Bash` command string, a `Write` `content`, or a `WebFetch` `url` all return `permissionDecision: "deny"`; a different random UUID passes through untouched; a missing canary file falls through unchanged to the stage-2 heuristic behavior above.
- `cursor_mirror.mjs` is load-bearing in a quieter way — it's the only thing keeping `.cursor/rules/` honest, and a bug there means Cursor sessions silently run on stale or broken rules. If you change it, test: a rule with no `paths:` gets `alwaysApply: true` and no `globs:`; a brace set expands to one glob per alternative with no `{`/`}` surviving (`globs` is comma-separated, so an unexpanded `**/*.{ts,tsx}` parses as two broken patterns — this is the bug most worth a regression test); quoted YAML paths lose their quotes; output is `.mdc`, never `.md` (Cursor ignores `.md` under `.cursor/rules/`); `--check` exits 1 on a missing, stale, or orphaned mirror and **writes nothing** in any of those cases; a bare run removes an orphan whose `.claude/rules/` source was deleted; and two consecutive bare runs are byte-identical. The recipe is in `bigin-harness-setup/references/cursor-parity.md` → `## Testing the mirror by hand`.
- Plugin-level `agents/*.md` frontmatter is the **default** ladder (`opus-centric` profile — quick `sonnet`/low, standard `opus`/medium, deep `opus`/high, verifier `sonnet`/high); `model-router` overrides `model` per spawn from `.claude/model-routing.json`, so keep frontmatter and `references/model-profiles.md` in sync. Never pin `effort` on a `model: haiku` agent expecting it to apply: Haiku 4.5 doesn't accept an effort level.
- **`effort` has no call-site override**, so a profile that wants a tier at a different effort routes to an **effort variant** — a second agent file, same role, different pin (`standard-worker-high`, `verifier-medium`). A variant's body must be byte-identical to its base and its frontmatter may differ only in `name` and `effort`; `tools/docs_sync.mjs --check` fails the commit otherwise. Edit the base, then copy its body over — never patch a variant alone, and keep body prose effort-agnostic so both files can carry it. Adding one means the variant file plus its `AGENTS` entry in `skills/model-router/scripts/classify.mjs` (and a `docs-manifest.json` entry); `docs_sync.mjs` imports `EFFORTS`/`AGENTS` from there rather than restating them, and fails closed on an effort with no agent, an agent with no file, a frontmatter effort that disagrees with the map, and body/frontmatter drift.
- **`high` is the documented default effort on every model that supports effort** (only Opus 4.7 defaults to `xhigh`). Any pin away from `high` needs a stated reason in `references/model-profiles.md` — `low` for genuinely mechanical, latency-sensitive tiers, `medium` for pattern-following work that an approved `PLAN.md` plus the verifier round already constrains. **`high` is the ceiling — no tier pins to `xhigh` or `max`, ever.** Not for the deep tier, not for a new agent, not "just for this one." The checking an above-default pin would buy is supplied structurally by the implement/verify loop, and above-default effort buys hedging and overthinking on top of it. A task that seems to need more effort is an under-specified `PLAN.md` or a missing convention — fix that instead. Don't assert what a model's default is from memory; it's in the model-config docs.
- **Model choice answers "could it do this at all"; effort answers "did it check its work."** Keep routing signals on the axis they actually predict — breadth, coverage, and blast radius set the verification bar, not the model tier.
- For agents generated *into target repos*: `architect`-style agents get `model: opus`; others `model: sonnet`. QA/reviewer agents restrict `tools:` to `Read, Grep, Glob, Bash` (no Write/Edit) rather than relying on prose to enforce read-only behavior. `agentType` is not a subagent frontmatter field — it only applies as a call-site option when *invoking* an agent (e.g. `Agent` tool `subagent_type`, `Workflow`'s `agent()` `opts.agentType`), never inside a `.claude/agents/*.md` definition's own frontmatter.

**Key skill facts:**

- `bigin-harness-setup` is idempotent — never clobbers without confirmation; `settings.json` merged, `README.md` append-only
- `nuxt-scaffold` owns the Nuxt project (config, sample code, hooks); governance stays with `bigin-harness-setup`
- `sprint-distill` compresses, never appends — every addition names what it replaces or cites budget headroom
- `epic-workflow` adds **no gate**. Approving an epic approves the decomposition only, and `.claude/memory/EPIC.md` must never be made to satisfy `spec-gate-guard.mjs` — every unit keeps its own root `PLAN.md` and faces the gate on its own merits. The queue file is deliberately outside the repo root (units land on different branches) and carries no `Branch:` line.
- `task-workflow`'s course-correction path **reuses `Status:`** rather than adding a freeze mechanism: `spec-gate-guard.mjs` passes only `approved`, so `amending` blocks by itself. Don't introduce a second flag, and don't teach the guard a new status — any value other than `approved` already blocks.
